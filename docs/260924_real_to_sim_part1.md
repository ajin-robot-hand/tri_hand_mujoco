# Verification Guide: Real-to-Sim Transfer (Part 1: Kinematics & Actuation)

> **문서 개요**: 실물 하드웨어 로봇(`tri_hand`)을 물리 시뮬레이터(MuJoCo)로 옮길 때 반드시 검증해야 하는 **기구학(Kinematics), 동역학(Dynamics), 액추에이터(Actuator) 모델링 원리**를 다룹니다.  
> 초보자가 이해하기 쉽도록 개념의 정의, 물리적 인과관계, 불일치 시 발생하는 문제, 그리고 `tri_hand` 실무 적용 방안을 단계별로 설명합니다.

## Overview: 현실 로봇을 가상 공간으로 옮기는 의미

로보틱스 분야에서 시뮬레이션은 단순한 3D 시각화 도구가 아닙니다. 실물 로봇을 위험 없이 제어하고 학습시키기 위한 **정밀 물리 실험실**입니다.

### 1. 시뮬레이션 관련 핵심 3대 용어

시뮬레이션 전이(Transfer)와 관련된 용어는 방향성과 목적에 따라 명확히 구분됩니다.

```
       [Real-to-Sim] (물리 특성 측정 및 가상 모델 튜닝)
 현실 로봇 ==============================================> 가상 시뮬레이터 (MuJoCo)
 (Hardware) <============================================== (Simulation)
       [Sim-to-Real] (가상에서 검증된 제어기/정책 배포)

             [Sim-to-Sim] (물리 엔진 간 상호 검증 및 비교)
 가상 시뮬레이터 A (MuJoCo) <============================> 가상 시뮬레이터 B (Isaac Gym 등)
```

| 구분 | 용어 | 정의 및 목적 |
| :--- | :--- | :--- |
| **Real-to-Sim** | 현실에서 가상으로 | 실제 조립된 하드웨어의 치수, 질량, 모터 출력 한계, 마찰 등을 정밀 측정하여 시뮬레이터에 일치시키는 과정 (**본 가이드의 핵심**) |
| **Sim-to-Real** | 가상에서 현실로 | 시뮬레이터에서 최적화하거나 강화학습으로 훈련한 제어 알고리즘(Policy)을 실제 하드웨어에 안전하게 배포하는 과정 |
| **Sim-to-Sim** | 가상에서 가상으로 | 서로 다른 물리 엔진(예: MuJoCo vs Isaac Gym vs PyBullet) 간에 동일한 제어기가 동일하게 작동하는지 비교 검증하는 과정 |

### 2. 현실 간극(Reality Gap)이란 무엇인가?

* **정의**: 시뮬레이터 상의 가상 로봇과 현실의 실제 로봇 사이에 존재하는 물리적 거동의 차이(Discrepancy)를 의미합니다.
* **발생 원인**:
  1. **단순화된 수학 모델**: 시뮬레이터는 연산 속도를 위해 전선 저항, 미세한 기어 백래시(유격), 프레임의 탄성 변형 등을 단순화하거나 무시합니다.
  2. **부정확한 파라미터**: 질량, 무게중심, 마찰 계수, 모터 감속기 관성 등을 실측하지 않고 어림짐작으로 입력할 때 발생합니다.
* **현실 간극을 방치했을 때의 위험성**:
  * 시뮬레이션에서 완벽히 성공한 파지(Grasping) 동작이 실제 로봇에서는 물체를 떨어뜨리거나 놓칩니다.
  * 가상 환경에서 학습된 제어기가 현실 모터의 물리적 한계를 초과하는 과도한 토크를 요구하여 모터가 타거나 감속기 기어가 파손될 수 있습니다.

## Chapter 1. 기구학 및 기하학적 정합성 (Kinematics & Geometric Fidelity)

로봇의 뼈대와 외형이 현실과 일치하지 않으면, 이후 수행하는 모든 동역학 계산과 궤적 제어가 어긋납니다.

```
[CAD 모델 / 실물 로봇]                 [MuJoCo 가상 모델]
 ├─ 모터 출력축 중심 (실측)   ──(일치)──>  <joint pos="..." axis="...">
 ├─ 기구적 스토퍼 한계각     ──(일치)──>  <joint range="min max"/>
 └─ 3D 형상 (외형 vs 접촉)   ──(분리)──>  Visual Mesh(STL) + Collision Geom(Box)
```

### 1.1 조인트 피벗(Pivot)과 회전축(Axis)의 정합

#### (1) 개념 정의
* **피벗(Pivot, `pos`)**: 관절이 회전하는 중심점의 3차원 좌표입니다.
* **회전축(Axis, `axis`)**: 회전이 일어나는 단위 벡터입니다 (예: `1 0 0`은 +X축 회전).

#### (2) 왜 반드시 정밀 일치해야 하는가?
* 관절 회전 중심과 힘이 작용하는 지점 사이의 거리를 **모멘트 암(Moment Arm, $r$)**이라고 합니다.
* 로봇이 낼 수 있는 회전력(토크, $\tau$)은 모멘트 암과 작용력의 외적($\tau = r \times F$)으로 결정됩니다.
* 피벗 위치가 실물 모터 축 중심에서 단 5mm만 어긋나도:
  * 손끝(Fingertip)의 위치를 계산하는 순기구학(Forward Kinematics) 오차가 발생합니다.
  * 목표 지점에 도달하기 위한 역기구학(Inverse Kinematics) 계산이 왜곡됩니다.
  * 손끝에서 물체를 누르는 접촉력(Contact Force)의 크기와 방향이 완전히 달라집니다.

#### (3) `tri_hand` 실무 적용
* `src/hand.xml`에서 모든 손가락의 굴곡(Flexion) 관절은 `axis="1 0 0"`(+X축)으로 회전합니다.
* 엄지 손가락의 요(Yaw/대립) 관절인 `A_j0`는 모터 혼의 회전축인 Y축(`axis="0 1 0"`)을 중심으로 회전합니다.
* 실물 모터(Dynamixel XL430)의 출력축 센터를 3D CAD 원점과 정확히 일치시켜 `<joint pos="...">`를 정의해야 합니다.

---

### 1.2 관절 가동 범위(Mechanical Limits)와 물리적 스토퍼

#### (1) 개념 정의
* 관절이 회전할 수 있는 최소각과 최대각의 한계입니다 (`range="min max"`).

#### (2) 초보자가 자주 하는 실수: 모터 리밋 vs 기구적 스토퍼
* 서보 모터(XL430)는 소프트웨어 설정상 360도 전 구간 회전이 가능합니다.
* 하지만 실제 3D 프린팅된 핑거 프레임이 결합되면, 링크끼리 물리적으로 맞부딪히는 **하드웨어 기구적 스토퍼(Mechanical Stopper)**가 존재합니다.
* 시뮬레이터에 실물 하드웨어 스토퍼 각도를 지정하지 않으면:
  * 제어기가 링크가 서로 파고드는 불가능한 각도로 명령을 보냅니다.
  * 실제 로봇에 이 명령이 전달되면 모터가 링크를 억지로 꺾으려다 과부하(Overload Error)로 정지하거나 부품이 부러집니다.

#### (3) `tri_hand` 실무 적용
* `src/hand.xml`의 기본 설정:
  ```xml
  <joint type="hinge" axis="1 0 0" range="-1.5708 1.5708" limited="true"/>
  ```
* 실제 로봇의 전원을 끄고 손으로 손가락을 완전히 접고 폈을 때 프레임이 부딪히는 각도를 각도기 또는 모터 엔코더로 측정하여, `range` 값을 하드웨어 한계보다 2~3도 안쪽으로 안전하게 설정해야 합니다.

### 1.3 시각 메쉬(Visual)와 물리 충돌체(Collision)의 분리 원칙

MuJoCo 모델링에서 가장 중요한 황금률 중 하나는 **"눈에 보이는 것과 충돌을 계산하는 것을 철저히 분리하는 것"**입니다.

| 구분 | 시각용 지오메트리 (Visual Geom) | 충돌용 지오메트리 (Collision Geom) |
| :--- | :--- | :--- |
| **목적** | 사람의 눈에 로봇 외형을 사실적으로 보여줌 | 물리 엔진이 관통 방지 및 접촉력을 계산함 |
| **형상** | 수만 개의 폴리곤을 가진 3D STL 메쉬 | 단순한 수학적 기본 도형 (Box, Cylinder, Sphere) |
| **MuJoCo 설정** | `group="1" contype="0" conaffinity="0"` | `group="3" contype="1" conaffinity="1"` |
| **연산 비용** | 렌더링 GPU 연산 (물리 연산 영향 없음) | 매 타임스텝(0.002초)마다 수치 솔버가 연산 |

#### 복잡한 STL 메쉬를 충돌체로 직접 쓰면 안 되는 이유
1. **연산 속도 급락**: 수만 개의 미세 삼각형 면(Triangle) 각각에 대해 충돌 여부를 검사하므로 시뮬레이션이 극도로 느려집니다.
2. **수치적 불안정성과 튕김**: 표면이 울퉁불퉁한 STL 메쉬끼리 부딪히면 접촉 법선 벡터(Normal Vector)가 순간순간 무작위로 튀어, 물체가 총알처럼 튕겨 나가거나 시뮬레이션이 발산(`NaN`)합니다.
3. **접촉 관통(Tunneling)**: 얇은 삼각 메쉬는 고속 충돌 시 서로 뚫고 지나가는 관통 현상이 발생하기 쉽습니다.

> 💡 **CAD 및 기하학 심화 참고 가이드**:  
> CAD 모델의 현실 크기 스케일링 법칙($L^4$ 중력 토크, $L^5$ 관성 모멘트 급증)과 어셈블리 장착면 밀착(7.1mm 조립 오차 사례)에 대한 상세 분석은 [기하학적 형상과 현실 크기 반영 가이드](./geometric_fidelity_and_scale_in_simulation.md)를 참고하세요.

## Chapter 2. 동역학 및 관성 특성 (Inertial & Passive Dynamics)

형상이 맞더라도 질량과 무게중심이 틀리면, 같은 토크를 가했을 때 가속도와 거동이 완전히 달라집니다.

```
       [로봇 다체 동역학의 기본 지배 방정식]
       M(q) * q_acc + c(q, q_vel) = tau_actuator - tau_external

 M(q): 관성 행렬 (Mass Matrix) -> 링크 질량, CoM, diaginertia, armature의 함수
 c(q, q_vel): 코리올리 및 원심력, 중력 벡터
```

### 2.1 질량(Mass), 무게중심(CoM), 관성 모멘트(Inertia Tensor)

#### (1) 개념 정의
* **질량(Mass, $m$)**: 물체가 가속도에 저항하는 정도(병진 운동 저항).
* **무게중심(Center of Mass, CoM)**: 물체의 모든 질량이 집중된 것으로 볼 수 있는 평균 위치.
* **관성 모멘트(Inertia Tensor, $I$)**: 물체가 회전 운동에 저항하는 정도. 회전축과 질량 분포 거리에 따라 달라집니다 ($I = \int r^2 dm$).

#### (2) 3D 프린팅 복합 구조체의 모델링 주의점
* `tri_hand`의 손가락 링크는 **가벼운 3D 프린팅 플라스틱 프레임(약 10~15g)**과 **무거운 모터 본체(XL430: 약 57g)**가 결합된 형태입니다.
* 3D CAD에서 단순히 균일한 플라스틱 밀도로 계산하면, 실제로는 모터가 위치한 쪽으로 치우쳐 있는 무게중심(CoM)을 완전히 잘못 예측하게 됩니다.
* **실무 팁**:
  * 손가락 링크 1개 조립체 전체의 실제 무게를 전자저울로 측정합니다 (약 70g = 0.07kg).
  * 무게중심(`pos`)을 모터 코어 쪽에 가깝게 배치하고, 주축 관성 모멘트(`<inertial diaginertia="..."/>`)를 입력합니다.

---

### 2.2 모터 감속기와 로터 반사 관성 (`armature`)

이 개념은 **로봇 공학 시뮬레이션에서 초보자가 가장 많이 놓치는 핵심 파라미터**입니다.

#### (1) 반사 관성(Reflected Inertia)의 물리적 원리
* 소형 서보 모터는 작은 토크로 큰 힘을 내기 위해 내부에 높은 감속비의 기어박스를 사용합니다.
* Dynamixel XL430-W250-T의 감속비는 무려 **$N = 258:1$**입니다. 즉, 관절이 1바퀴 돌 때 내부 전기 모터 로터(회전자)는 258바퀴를 돕니다.
* 회전 운동 에너지는 속도의 제곱에 비례하므로, 관절 축에서 바라본 모터 로터의 유효 관성은 감속비의 제곱($N^2$)으로 확대됩니다:
  $$I_{\text{reflected}} = N^2 \cdot I_{\text{rotor}}$$
* $258^2 \approx 66,564$배라는 막대한 비율로 로터의 작은 관성이 증폭되어 관절에 작용합니다.

#### (2) `armature`가 누락되었을 때 발생하는 문제
* MuJoCo의 `<joint armature="..."/>` 속성이 바로 이 $I_{\text{reflected}}$를 나타냅니다.
* `armature` 값을 0이나 지나치게 작은 값으로 두면:
  * 시뮬레이터는 손가락이 깃털처럼 가볍다고 판단하여, 작은 힘에도 비현실적으로 급가속합니다.
  * 물체와 부딪히는 순간 관절이 진동(Chattering)하며 튕겨 나갑니다.
* `src/hand.xml`의 설정:
  ```xml
  <joint damping="0.15" armature="0.01"/>
  ```
  이 `armature="0.01"`은 고감속 기어박스의 유효 관성을 대변하여 관절 운동을 수치적으로 안정시키고 실물의 묵직한 거동을 재현합니다.

### 2.3 수동 감쇠(`damping`)와 기계적 마찰(`frictionloss`)

#### (1) 개념 정의
* **감쇠(Damping, $b$)**: 속도에 비례하여 운동을 방해하는 저항력 ($F = -b \cdot \dot{q}$). 베어링 오일의 점성 저항 등.
* **마찰 손실(Friction Loss, $f_c$)**: 속도 방향과 반대로 작용하는 일정한 건식 마찰(Coulomb Friction). 기어의 맞물림 저항.

#### (2) 실무 검증 방법
* 전원이 꺼진 실물 로봇 손가락을 특정 각도까지 들어 올렸다가 손을 놓았을 때, 중력에 의해 떨어지는 양상을 관찰합니다:
  * 멈추지 않고 진자처럼 여러 번 흔들리며 떨어지면 `damping`이 부족한 상태입니다.
  * 실물 로봇은 기어 저항 때문에 거의 진동 없이 스르륵 떨어지거나 특정 각도에서 마찰로 멈춥니다.
  * 이 거동을 시뮬레이터와 일치시키는 것이 동역학 튜닝의 첫걸음입니다.

## Chapter 3. 액추에이터 및 구동계 동특성 (Actuator Dynamics & Control)

시뮬레이션의 제어기가 아무리 훌륭해도, 실물 모터가 낼 수 없는 출력을 요구한다면 현실에서 동작할 수 없습니다.

```
[제어기 목표 각도 q_des] 
       │
       ▼
[MuJoCo 액추에이터: PD 제어] ───> tau = kp * (q_des - q) - kv * q_vel
       │
       ▼
[토크 포화 (Saturation)]     ───> clamp(tau, -1.4 N·m, +1.4 N·m)
       │
       ▼
[관절 모터 구동]
```

### 3.1 이상적인 토크 소스 vs 현실의 서보 모터

* **이상적인 시뮬레이션 가정**: 제어기가 원하는 토크를 지연 없이, 무한한 크기로 즉각 생성할 수 있다고 가정하기 쉽습니다.
* **현실 서보 모터(XL430)의 물리적 한계**:
  1. **최대 정격 토크 한계 (Stall Torque)**:
     * XL430은 12V 인가 시 최대 1.4 N·m 이상의 토크를 절대 낼 수 없습니다.
     * MuJoCo 액추에이터에 `forcerange="-1.4 1.4"`를 강제해야 합니다.
  2. **무부하 최고 속도 한계 (No-load Speed)**:
     * 전동기는 역기전력(Back-EMF) 현상으로 인해 회전 속도가 빨라질수록 낼 수 있는 토크가 감소하며, 최대 속도(XL430 기준 약 61 RPM $\approx 6.38\text{ rad/s}$)를 넘을 수 없습니다.

---

### 3.2 서보 위치 제어 게인(`kp`, `kv`)과 관절 순응성(Compliance)

#### (1) MuJoCo `<position>` 제어기의 동작 원리
MuJoCo의 position 액추에이터는 내부적으로 다음과 같은 PD 제어 법칙으로 토크를 생성합니다:
$$\tau = k_p (q_{\text{target}} - q) - k_v \dot{q}$$

* **$k_p$ (Proportional Gain, 강성)**: 목표 각도와의 오차에 비례해 힘을 발생시키는 가상 스프링.
* **$k_v$ (Derivative Gain, 감쇠)**: 관절 속도에 비례해 저항을 주어 오버슈트(목표 각도를 지나침)를 억제하는 가상 댐퍼.

#### (2) 관절 순응성(Compliance)의 중요성
* 로봇 손이 물체를 쥘 때 모터는 목표 위치에 도달하지 못하고 물체 표면에 가로막힙니다.
* 이때 발생하는 각도 오차($e = q_{\text{target}} - q$)에 $k_p$가 곱해져 **물체를 쥐는 파지력(Grasping Force)**으로 변환됩니다.
* 실물 Dynamixel의 내부 Position P Gain 값과 MuJoCo의 `kp` 값을 조율하여, 손가락 끝으로 물체를 눌렀을 때 밀려나는 탄성 정도(Compliance)가 현실과 같아야 합니다.

---

### 3.3 제어 루프 주기(Control Rate)와 통신 지연(Latency)

* **물리 적분 주기 (Physics Timestep)**:
  * MuJoCo는 물리적 연속성을 위해 기본 `timestep="0.002"` (500Hz, 매 2ms) 단위로 미분 방정식을 풉니다.
* **실제 제어 통신 주기 (Control Loop Rate)**:
  * 실제 로봇 하드웨어는 USB-to-RS485(U2D2 등) 시리얼 버스를 통해 모터 7개의 패킷을 주고받습니다.
  * 통신 대역폭 한계로 인해 실제 제어 명령 갱신 주기는 통상 **50Hz ~ 100Hz (10ms ~ 20ms)** 수준입니다.
* **영차 홀드(ZOH: Zero-Order Hold) 검증**:
  * 제어기가 500Hz로 매 순간 각도를 수정할 수 있다고 가정하면 안 됩니다.
  * 10~20ms 동안 이전 제어 입력이 유지(ZOH)되는 환경에서도 제어기가 진동 없이 안정적인지 검증해야 합니다.

---

### 3.4 [실무 하드웨어 연계] 액추에이터 설정의 이원화: Wizard(EEPROM) vs 코드(RAM)

앞서 살펴본 최대 토크, P/D 제어 게인, 통신 속도(Baudrate) 같은 파라미터를 실제 로봇 하드웨어(Dynamixel XL430)에 적용할 때, 초보자가 가장 많이 하는 질문은 **"이 설정들을 GUI 프로그램(Wizard)으로 해야 하는가, 아니면 파이썬 코드로 해야 하는가?"**입니다.

결론은 **"액추에이터의 메모리 구조(EEPROM vs RAM)에 따라 역할 분담"**을 해야 합니다.

```
[Dynamixel XL430 내부 메모리 구조]
 ├── 1. EEPROM 영역 (비휘발성: 전원 꺼져도 영구 보존) ──> DYNAMIXEL Wizard 2.0 (초기 1회성 셋업)
 │    ├─ 모터 ID (ID 1 ~ 7)
 │    ├─ 통신 속도 (Baudrate: 기본 57,600 -> 1,000,000 bps)
 │    └─ 하드웨어 안전 리밋 (전압 한계, 온도 한계)
 │
 └── 2. RAM 영역 (휘발성: 전원 끄면 초기화)         ──> Python 제어 코드 (런타임 제어)
      ├─ 토크 활성화 (Torque Enable = 1 / 0)
      ├─ 런타임 제어 게인 (Position P/D Gain)
      ├─ 목표 지령 (Goal Position, Goal Velocity)
      └─ 상태 모니터링 (Present Position, Present Current)
```

#### (1) DYNAMIXEL Wizard 2.0으로 해야 하는 작업 (초기 하드웨어 셋업)
* **공장 출하 상태의 함정**:
  * 새로 구매한 모든 다이나믹셀 모터는 공장 출하 시 **기본 ID가 전부 '1'**, 통신 속도는 **'57,600 bps'**로 통일되어 있습니다.
  * 모터 7개를 프레임에 조립하고 케이블로 줄줄이 연결(Daisy-chain)한 채 전원을 켜면, 모든 모터의 ID가 1번으로 충돌하여 통신 자체가 불가능해집니다.
* **초기 셋업 절차**:
  1. 로봇 프레임 조립 전(또는 케이블을 1개씩만 연결한 상태에서), 모터를 PC와 1:1로 연결합니다.
  2. DYNAMIXEL Wizard 2.0을 실행하여 각 모터에 **고유 ID(1번부터 7번까지)**를 순차적으로 부여합니다.
  3. 통신 속도(Baudrate)를 기본 `57,600 bps`에서 **`1,000,000 bps (1 Mbps)`**로 변경하여 저장합니다.
* **왜 위자드가 안전한가?**:
  * EEPROM은 비휘발성 영역이므로 1회만 설정하면 영구 고정됩니다.
  * GUI 환경에서 펌웨어 업데이트, 모터 과열/과전압 에러 자가진단을 직관적으로 수행할 수 있습니다.

#### (2) 파이썬 코드(Dynamixel SDK)로 해야 하는 작업 (런타임 운영)
* **프로그램 생명주기 관리**:
  * 제어 스크립트 시작 시: 통신 포트 오픈 $\to$ `Torque Enable = 1` 인가 $\to$ 안전 프로파일(속도/가속도 한계) 주입.
  * 제어 루프 실행 중: 매 주기(예: 10ms)마다 `SyncWrite`로 7개 모터의 `Goal Position` 일괄 전송, `SyncRead`로 `Present Position/Current` 일괄 수신.
  * 프로그램 종료 시: 반드시 `Torque Enable = 0`으로 토크를 해제하여 모터 발열 및 과부하 방지.
* **런타임 제어 게인 주입**:
  * MuJoCo의 `kp="12"` 설정에 대응되는 Dynamixel의 `Position P Gain` 값을 코드 시작 시 모터들에 일괄 주입함으로써, 소프트웨어 버전이나 실험 목적에 따른 게인 튜닝을 코드로 재현 가능하게 관리합니다.

#### (3) 코드로도 모터 ID나 보드레이트(EEPROM)를 바꿀 수 있는가?
* 기술적으로는 가능합니다. 파이썬 SDK로 EEPROM 영역(Address 7: ID, Address 8: Baudrate)에 Write 패킷을 보낼 수 있습니다.
* 단, 다음 조건과 위험이 따릅니다:
  1. 반드시 **`Torque Enable = 0` (토크 차단 상태)**에서만 EEPROM 쓰기가 허용됩니다.
  2. 코드로 보드레이트를 변경하는 순간 모터의 통신 속도가 즉시 바뀌므로, PC의 통신 포트도 즉시 동일 속도로 다시 열어야 통신이 유지됩니다.
  3. 코드로 일괄 변경하다 패킷 에러나 오타가 발생하면 모터의 ID/속도가 꼬여 프로그램에서 인식되지 않는 "벽돌(Bricked)" 상태처럼 보이며, 결국 위자드를 켜서 1개씩 검색해 복구해야 합니다.
* **실무 권장**: 개발 및 프로토타입 단계에서는 **"위자드로 ID/보드레이트 1회 고정 $\to$ 코드로 실시간 제어"**라는 명확한 역할 분담을 지키는 것이 가장 안전하고 효율적입니다.

## Part 1 자체 점검 체크리스트 (Self-Checklist)

팀원들은 시뮬레이션 모델을 수정할 때 다음 항목을 반드시 대조 확인해야 합니다:

- [ ] **회전축 일치**: 모든 관절 회전축이 CAD 도면 및 실물 모터 축 방향(`+X` 또는 `+Y`)과 일치하는가?
- [ ] **기구학적 한계**: 관절 가동 범위(`range`)가 3D 프린팅 프레임 간의 물리적 충돌 스토퍼를 반영하고 있는가?
- [ ] **충돌체 분리**: 시각용 메쉬(`group 1`)와 물리 충돌체(`group 3`)가 명확히 분리되어 있으며, 충돌체에 복잡한 STL 메쉬를 사용하지 않았는가?
- [ ] **반사 관성 설정**: 고감속 기어박스를 반영하는 `<joint armature="...">` 값이 적절히 부여되어 있는가?
- [ ] **액추에이터 포화**: `<position forcerange="-1.4 1.4"/>`로 실제 모터의 최대 토크 한계가 제한되어 있는가?
- [ ] **하드웨어 셋업(Wizard)**: 모든 모터에 중복 없는 고유 ID(1~7)가 부여되었으며, Baudrate가 1,000,000 bps(1 Mbps)로 통일되어 있는가?
- [ ] **런타임 코드 분리**: EEPROM 영구 설정(ID/Baudrate)과 RAM 실시간 명령(Torque, Goal Position, P/D 게인)이 명확히 분리되어 제어되는가?
